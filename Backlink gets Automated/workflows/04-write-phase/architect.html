Content Machine · Write Phase · Station 2

The Architect

The planner hands over a pile of approved sub-topics with their evidence. The architect turns that pile into the article's real skeleton: which sections exist, in what order, how long each one runs, which ones deserve a search keyword, and the exact words of every heading and the H1. It designs the body and nothing else. Here is how it works, script by script.

01The one idea

Five moves, in order. Each writes a file the next one reads, so a crash resumes where it stopped and you can open any file to see what that step decided.

🧱

Design the body

Every approved sub-topic becomes a numbered box. The AI arranges the boxes into sections, in reading order, and benches what the article does not need.

🔎

Fill the holes

Where the design says a section is thin, it searches the web, reads the pages, and builds new evidence cards with their source links.

📏

Budget the words

Each section gets a word target, set by how much it matters to the argument, not by how much evidence it happens to hold.

✍️

Name everything

It works out which sections a stranger would search for, buys one keyword for those, then writes every final heading and the H1 last.

The one rule that governs everything

The architect arranges, it never invents. Every section it builds is made of boxes the planner already approved, and every box traces back to a research card with a source. The only new material that can enter is a card the enrich step fetched from a real page it downloaded, and those carry their link. If a fact cannot be traced to a card, it does not exist here.

02The words you need first

Six terms carry this whole page. Each is defined once and then used exactly.

Card — one atomic fact, with the sentence it came from and the link to the page that said it. Cards are made in the research phase; the architect moves them around and can add new ones, but never edits what a card says.
Box — one approved sub-topic (an H3) with all its cards attached, given a number (#1, #2, #3…). The AI that designs the structure answers only in box numbers, so it cannot quietly invent a topic: a number either exists or the code rejects it.
The spine — one short paragraph saying what this article argues, for whom, and what the reader can do at the end. The architect writes its own, after seeing which boxes actually survived.
The world — two lines, about and not about, written back in the research phase before any searching started. They mark the boundary of the article's subject, so material from a neighbouring field that happens to share our words can be recognised and thrown out.
Archetype — the shape family this page belongs to: a how-to guide, a listicle, a comparison, a template, and so on. It decides which road the design step takes.
KD (keyword difficulty) — a 0-100 score from the search-data provider estimating how hard a phrase is to rank for. Paired with search volume, the monthly number of people who type it.

03The architecture

One entry command, five step scripts, three shared files. Nothing else.

FileWhat it is for
run_architect.py The one command. Calls each step's run() in order and does nothing else. It prints the step name as it goes, times each one, and records it to the shared usage ledger.
config.py Every path and setting, in one place. All of it is worked out from a single anchor, so pointing the engine at a different company is one line. Every tunable here is a named constant with a comment.
llm.py The one AI caller. Runs prompts through the locally logged-in Claude or Codex command line, so there is no API key and no per-call cost. It reads prompts from prompts/, pulls JSON out of the reply even when the model wraps it in prose, and asks again once if the reply will not parse.
article_ctx.py The shared context reader. Hands every step the same five facts about the article: title, angle, spine, and the two world lines. Before it existed, each step worked out what it needed on its own and the world reached almost nothing.
dfs.py paid The only file that talks to the search-data provider. It lives with the research engine and is imported only when a step is about to spend money, so everything else still runs when those credentials are missing. It checks the account balance before it buys anything.

Who decides what

The split is deliberate. The AI is confined to judgment; everything countable is arithmetic, because arithmetic does not drift between runs.

🧠

The AI decides

Judgment calls a formula would get wrong
It answers
  • Which boxes group into which section, and in what order
  • What the article argues (the spine) and what each section's job is
  • What share of the article each section deserves
  • Whether a section is something a stranger would search for
  • The exact words of every heading and the H1
⚙️

Code decides

Anything that must be identical every run
It enforces
  • Every box number is real, and no box lands in two sections
  • Word targets: shares are turned into word counts that add up
  • A keyword only survives if a real heading actually took it
  • A heading may only claim a keyword it was shown
  • Every file is written to a temp name and renamed into place, so a half-written file can never exist
Resumable by design

Each step checks whether its output file already exists and reuses it if so. That is why the rename matters: a file existing has to mean it is complete, or a crash mid-write would leave a broken file that the next run silently trusts. Pass --redo to force every step to run again.

04The five steps

Run it with python3 run_architect.py --slug <slug>. The planner must have run first: this reads its frozen plan and never reaches back past it.

1

SHAPE — design the body free

Turns the approved sub-topics into numbered boxes, then asks the AI to build the article out of them: the spine first, then the sections in reading order, each with its job written before its heading, then the box numbers that go inside it.

  • Four roads by archetype, so a comparison and a how-to are not forced through the same prompt.
  • Benching is expected. A box the article does not need is left out, and any box that carried a promise or a hard number has to be justified in writing.
  • Research markers are raised here: a section that is genuinely thin names the sub-topics it is missing, and the next step goes and finds them.
scriptshape.py writes_work/structure.shaped.json

2

ENRICH — go and find what is missing paid

For every sub-topic the design flagged as missing, it plans web searches, fetches the result pages, downloads them, and builds new cards from what they actually say.

  • Nothing flagged means this step is instant: the shaped structure is simply promoted to final.
  • New cards get IDs from 9001 up, so an enriched fact is always distinguishable from a research-phase one.
  • A failure never spreads. One sub-topic whose search comes back empty is logged and skipped; the rest carry on.
scriptenrich.py writesstructure.jsonenriched-cards.json
↓ §06 — how a new card is built
3

ALLOCATE — budget the words free

The AI gives each section a percentage of the article, judged by how much it matters to the argument. Code turns the percentages into word counts.

  • The base is the middle of the word band, not the top of it. Handing out the ceiling leaves no room to cut anything later.
  • Evidence volume is explicitly not the measure. The prompt says so outright: a section with few cards can still be the heart of the piece.
  • A failed call falls back to an even split, so this step can never stall a run.
scriptallocate_words.py writes_work/word-allocation.json
4

SECTION KEYWORDS — which sections earn one paid

Two sub-steps. A free gate decides which sections are worth a paid lookup; only those go to the hunt.

a gate, one call, free › b hunt, per section, paid
  • Silence means no. A section the gate did not return a verdict for is not hunted, so a malformed reply can never turn into spending.
  • Returning nothing is a good answer. Both the gate and the picker are told so explicitly.
scriptsection_keywords.py writes_work/section-keywords.json
↓ §07 — the gate, the hunt, the headings
5

HEADINGS — write every heading, then the H1 free

One call per section, all at once, each seeing that section's full evidence. Then one final call writes the H1, having read every finished heading.

  • The evidence outranks the plan. A section's job was written before the research came back; where the two disagree the prompt says the evidence wins.
  • The H1 goes last for one reason: it must not promise something the finished headings do not deliver.
  • The keyword list is then computed in code from the headings that actually took one. Nothing gets on that list for merely existing.
scriptheadings.py writesstructure.json_work/heading-map.json

05Shape — the boxes and the four roads

This is the step that decides what the article is. Everything after it is refinement.

Why boxes

Asking an AI to "design an article from this research" invites it to write whatever it likes and attach evidence afterwards. Numbering every approved sub-topic and demanding the answer come back as box numbers inverts that: the material is fixed, and the only freedom is arrangement. Code then checks every number it returns, warns when one box was put in two sections, and audits which boxes went unused.

Real run — the hackathon article

79 boxes went in. The design came back with 28 sections and 1 box benched with a written reason, and raised no research markers because nothing was thin.

The four roads

All four share the same core prompt text and the same output shape. They differ only in what extra work happens first and what extra field comes back.

RoadArchetypesWhat happens before the design callExtra output
Simple how-to guide · answer-bait · data report · glossary · common-spine Nothing. One design call. —
Listicle listicle An AI pass finds the actual list items in the evidence, merges near-duplicates, and drops any item the material only mentions in passing. A per-item contract: the labelled parts every item must end with, taken from what the angle promised.
Comparison comparison-rankings Three passes in a row:
  • name the options a buyer would shortlist
  • choose the 4-6 yardsticks they would be measured on
  • drop any option the evidence cannot speak to for at least 60% of those yardsticks
 Each surviving option gets its own section.
Template template-resource Nothing extra before the call. The artifact spec: what kind of file the download is, and which boxes go inside it rather than on the page.
The fairness rule

On the comparison road, when our own brand is one of the options it is treated as an option like any other. It keeps its section, it appears in every table and ranked list the rivals appear in, and it is judged on the same yardsticks. It may score below a rival, and the prompt says to write that plainly. A grid that scores every competitor but quietly omits the publisher reads as though the publisher has something to hide. When the article compares something we do not sell against, the rule switches off entirely so the brand is not inserted where it does not belong.

What the design step returns

spine
What the whole article argues, for whom, and what the reader can do at the end. Written first, because every section has to serve it.
sections[].job
What this section must deliver and how it moves the argument. Written before the heading, so the heading names something that already exists.
sections[].headline
A working heading. Step 5 replaces it with the real one, once the evidence is final.
sections[].boxes
The box numbers inside this section. Code validates every one.
sections[].needs_research
The sub-topic titles this section is missing. Used as written by the enrich step.
benched
Every box left out that carried a promise or a hard number, each with one line saying why.
Two spines, on purpose

The research phase already wrote a spine, before a single card existed. This one is written after, by a step that can see what actually came back. They are a plan and the plan corrected by reality, not a duplicate. The world is the opposite case: it is decided once, in the research phase, and every step here only reads it.

06Enrich — building a new card from scratch

The only step that can add material the research phase never found. Five moves per missing sub-topic, run one sub-topic at a time.

1

Plan the searches

Up to 3 web queries per missing sub-topic, phrased the way people actually search: short, concrete, varied, so one dead end does not sink the topic.

  • The prompt carries the world, with an instruction to put the setting or the audience inside the query itself. A bare query on a word two industries share returns the other industry's pages, and every card built from them looks plausible and is wrong.
promptplan-queries.md
2

Search paid

Organic results only from the search-data provider, with the account balance checked first.

  • If the balance is below the floor, it falls back to a single web-search call through the local Claude command line rather than failing the run.
promptsearch-urls.mdfallback only
3

Download the pages

Results are interleaved across the queries by rank so no single query dominates, deduplicated, then fetched until 15 pages have loaded. The top 8,000 characters of each are kept.

4

Build the cards

The AI reads the downloaded pages and writes cards. As many as the material honestly supports, and an empty list when the pages turned up nothing.

  • One card, one page. Blending two sources into a single card is forbidden, because then neither link proves it. Several cards from the same page are fine.
  • Each card carries a one-line summary, the faithful detail with its numbers intact, and the page link exactly as it was labelled.
promptextract-cards.md
5

Validate and attach

Code checks that every card's link is a page that was actually downloaded, assigns IDs from 9001 up, and drops the new sub-topic into the section that asked for it.

  • That link check is the anti-fabrication guard: a card citing a URL nobody fetched is rejected outright.
Real run — the video-interview comparison

That article's design flagged real holes and the enrich step produced 107 new cards, each tied to a page it had downloaded. The other four articles in that batch raised no markers at all and skipped the step entirely, which is the normal case.

07Keywords and headings

The last two steps, and the ones with the most guards. They decide what the reader actually sees.

Why the keyword work happens here

It used to happen in the research phase, against the planned outline. That outline no longer exists by the time the article is built, so keywords were bought for sections that were later merged or deleted. Now nothing is bought until the sections are real and their evidence is final.

Step 4a — the gate free

One call over the whole article, asking one question per section: would a person type this section's subject into Google as its own search?

AnswerWhen
yes
  • It answers a question someone would ask outside this article
  • It names something people look up: a method, a number, a cost, a comparison
  • Someone could land on it from a search and be satisfied
no
  • It only makes sense inside this article's argument
  • It sets up, bridges, concludes or summarises
  • Its subject is the article's main keyword again from another side, which the H1 already owns
  • It is about our own product, or it is the closing pitch

The prompt states the expected shape of the answer outright: roughly a third to a half of sections should be yes, and saying yes to nearly all of them means being too generous. Most sections carry the argument rather than a search.

Step 4b — the hunt paid

Only gated-yes sections get here. Each runs on its own, in parallel:

1 seeds from the section's cards › 2 look each seed up › 3 filter by volume and difficulty › 4 pick one, or none
  • Seeds come from the evidence, not the heading. A section headed "pricing" whose cards are all commission percentages is a section about commission rates, and gets seeded that way.
  • Seeds must be 2 or 3 words. This is the single most important rule in that prompt, and it is there for a measured reason: the suggestions index matches on the phrase itself, so a four or five word seed returns almost nothing and the section ends up with no keyword at all. Seed the short head of the idea and let the index find the longer phrases around it.
  • The filter is arithmetic: at least 100 monthly searches, difficulty below 40. The best 25 survivors by volume are shown to the picker.
  • The picker chooses fit first, volume second, and is told that returning nothing is a good answer. A big number for a phrase the section does not answer just means the page ranks and the reader bounces.
Two guards on this step
  • Silence is not consent. A section the gate returned no verdict for is recorded as not hunted, so a malformed reply costs nothing rather than triggering spending.
  • You cannot pick what you were not shown. If the picker returns a phrase that was not in its candidate list, it is rejected and the section gets no keyword.

Step 5 — the headings

One call per section, all running at once, each seeing its section's job, its full evidence, its researched keyword, the leftover pool, and the article's main keyword. It may use any of them or none.

Order of preferenceWhat it is asked
1. This section's own keyword Does it name what this section delivers, and can the heading carry it without strain?
2. The leftover pool Does a keyword another section did not take fit this one better?
3. The main keyword or a reword Would it sit here naturally? It may, but the H1 already carries it.
4. None Write the best heading this section deserves on its own. A well-researched keyword that does not fit is still a keyword that does not fit.

The prompt bans the generic heading by name. "Overview", "Key considerations", "Things to know", "Best practices" and "Understanding X" are called out as the default an AI reaches for, with worked pairs showing the fix:

weak
Interview Question Considerations
strong
Questions to Ask a Candidate About Failure
weak
Understanding Cost Per Hire
strong
What a Bad Hire Actually Costs You

On length: the target is under 60 characters, because longer gets cut off in search results and skimmed past on the page. It is a target and not a wall. The prompt allows going over when the shorter version genuinely says less, and the code only records an over-length heading rather than rejecting it. Throwing away a specific, useful heading to save three characters is the worse trade.

Then the H1, last

One final call, after every heading is settled, seeing the whole list. It must carry the main keyword naturally and it must not promise something the headings do not deliver. If the planned H1 already carries the keyword, it comes back unchanged.

No cards are attached to the H1. Cards attach to sub-topics, sub-topics sit inside sections. The H1 is a promise about the article rather than a claim about the world, so the call that writes it never sees a single card.

The keyword list is arithmetic

After the headings are written, code walks them and collects the phrases that actually landed in one. Everything else is recorded as unplaced, with the reason "no section's heading took it". No AI gets to declare a keyword used.

Where this sits in the bigger machine

The planner decides what is worth writing about and freezes it. The architect decides what the article is: its sections, their order, their length, their names. The writer then decides how it reads, and it is not allowed to change any heading, because those were settled here with the evidence in view. Each station trusts the one before it and does not reach back past it.
