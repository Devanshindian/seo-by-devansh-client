How DataForSEO builds the keyword & SERP research brief

This is the engine that turns one asset topic into a fact-checked research brief — the keyword universe, the competitor map, the questions people actually search, and the gap we can own. Every number comes from a live search-data call, and every choice is scored by an AI panel, not picked on a hunch. Here is exactly how it is wired, script by script.

01The one idea

DataForSEO does not "ask an AI what keywords to target." It runs a disciplined research operation: pull the real search data, let an AI panel score the candidates against our topic and our brand, keep only the top ones, and save the scores as proof. Nothing is hand-picked on vibes.

The one rule that governs everything
No pick without a score, no number without a proof. The search API returns raw candidates; an AI sub-agent scores every one against the topic and the Testlify angle; we keep the top ones and save the scored list to disk. If a line in the final brief can't be traced back to a saved proof file, it doesn't belong.

End to end, the engine does seven things, then assembles them into one brief:

  1. Read the topic and turn it into seed phrases.
  2. Expand those seeds into the full keyword universe.
  3. Filter out the junk by search demand and difficulty.
  4. Score and rank what's left into a primary + supporting keywords.
  5. Read the live Google results page — who ranks, what questions appear.
  6. Read the top competitor pages to find the gap we can own.
  7. Check what AI assistants already answer for the topic.
Why it's cheap
The AI judgment (all the scoring and write-ups) runs on a headless LLM CLI for free — either Claude (the default) or Codex, whichever you point it at — no API key, no per-call fee. Only four steps spend money on the search-data API. A whole topic costs about $0.50–$1.00 — cheap enough to run on every asset.

02The words you need first

A few terms show up on every screen of this engine. Here they are in plain language, once.

Keyword volume — how many people search that phrase per month. High volume = more potential traffic. Below our floor of 100/month, we treat a phrase as too small to chase.
KD (keyword difficulty) — a 0–100 score for how hard it is to rank on page one. Big brands hold the high-KD terms; we target the low-KD ones we can realistically win (our ceiling is 40).
Intent — why someone searches a phrase: to learn (informational), to compare or buy (commercial). We keep informational + commercial, drop the rest.
SERP — the Search Engine Results Page: the actual Google page for a query. Reading it tells us who ranks, whether there's a featured snippet, an AI Overview, and the "People also ask" questions.
AI Overview / AEO — the AI-written answer box Google now shows above the results, and the answers AI assistants give. AEO = Answer Engine Optimization: getting cited in those answers. We check whether Testlify is cited (if not, that's a gap we can go win).
Headless LLM (Claude or Codex) — running a coding assistant from the command line with no chat window, so a script can call it. Either the Claude CLI (default) or the Codex CLI works, set by one --provider switch. This is how every judgment step ("score these", "write this up") happens for free — no API key.

This is the same self-contained layout every engine in the content machine uses: settings in config.py, credentials behind one client, AI behind one caller, prompts in their own files, and one pure-sequencing orchestrator. That's what makes the pipeline runnable unattended, on a schedule, and identical every run.

Why the chain matters
Each step's output is a named file the next step reads: seeds → pool → shortlist → keywords → SERP → winners → AEO → brief. That's what makes it resumable — if it stops after Step 4, re-running picks up at Step 5 and never repeats the paid calls it already made.

05Step 1 — the two nets that build the keyword universe

Seeds alone would only find phrases that literally contain the seed word. To reach the adjacent concepts that actually rank, we cast two different nets and merge them.

🕸️

The tight net

s1_expand.py · one call per seed

Asks the API for phrases that contain each seed — the on-topic long-tail for the pillar and each sub-topic. Good, but suffix-shaped: it only finds "seed + a word". Its quality depends entirely on the seeds, so ambiguous ones are qualified back in Step 0.

🏆

The ranked net

s1b_ranked.py · the workhorse

Takes the pages that already win — our competitor proof-URLs plus the top organic results for the seed — and pulls every keyword each of those pages ranks for. These are proven, on-topic phrases the seed net structurally can't reach: adjacent concepts like "hr scorecard" or "selection ratio formula". Usually the cleaner, richer source.

What we cut, and why
There used to be a third, wide net (the API's generic "keyword ideas"). We dropped it: across two live runs it returned 0 usable keywords out of 652 — pure job-search, plumbing and finance noise. Relevant breadth now comes entirely from the ranked net.

A note on two SERPs. The ranked net searches the seed to find winning pages; Step 4 later searches the primary keyword to read the real competitive landscape. Two different searches, on purpose — one finds keyword sources, the other reads the battlefield.

06Step 3 — the scoring panel and the judge

This is where the pipeline decides what to actually target. The filtered shortlist goes through a two-layer AI process: many scorers, then one judge. This is the "no pick without a score" rule in action.

📊

First, the real numbers paid

s3_metrics.py pulls exact volume, KD and intent for every shortlist survivor from the API. Keywords whose intent isn't informational or commercial are set aside.

🧑‍⚖️

Then the panel scores AI · free

s3_score.py splits the shortlist into batches and runs the scorer prompt over them across several headless-Claude sub-agents at once. Each scores a keyword 0–10 on relevance · distinctness · brand-fit (ignoring volume), then assigns a role. Every sub-agent's verdict is saved to its own file before judging — so the final picks are auditable back to the raw scores.

1batch the shortlist→ 2parallel sub-agents score each→ 3save every verdict to disk
✅

Then one judge reconciles AI · free

The same script's judge prompt reads all the verdicts + the numbers and makes the final call, breaking ties by volume. It outputs the keyword set below.

The four roles a keyword can get

RoleWhat it meansWhere it goes
PrimaryThe single highest-volume intent-match that clears the KD ceiling — not automatically the title phrase.The H1 term of the article.
VariationA reword or synonym of the primary — same intent.Woven into the body; no section of its own.
SecondaryA distinct, section-worthy sub-topic.Each one anchors its own section.
SpokeA distinct head term big enough for its own future article. Each is also scored + ranked (0.5 relevance / 0.25 volume / 0.25 ease; off-cluster heads scoring ≤2 dropped) so the research conductor keeps only the best 3.Saved, ranked, to spoke-candidates.md.
The tell for a good result
Good secondaries look like siblings ("iced coffee, coffee milkshake"), not the primary with a word tacked on ("cold coffee recipe easy, cold coffee recipe simple"). If the secondaries are all "primary + a word", the ranked net or the scorer under-performed — a built-in sanity check.

07Steps 4 & 5 — reading the battlefield

With the primary keyword chosen, the engine reads the real Google results page, then reads the winning competitor pages themselves — to map who ranks, what questions appear, and where the gap is.

Step 4 — the SERP snapshot paid

s4_serp.py pulls the live Google page for the primary (with the AI-Overview and People-also-ask flags on, or those blocks go missing). s4b_snapshot.py then writes it up. From one page it captures:

  • Who ranks — the top organic URLs; this is the literal competitor set.
  • Featured snippet — who holds the answer box, and its shape (paragraph / list / table), or "none — open to win".
  • AI Overview — present or absent, what it covers (our answer skeleton), and who it cites.
  • People also ask + related searches — tagged on-angle (FAQ/section candidates) vs off-angle, never silently dropped.
  • The read-list — the 3 best readable pages to open next (a #1 PDF or a forum thread is skipped), handed to Step 5.

Step 5 — read the winners, for free free

s5_pages.py fetches those 3 pages with a plain web request — no paid call, page reading is free — and parses their heading tree and word count. If a page blocks us it retries at least twice before falling back to the paid parser or swapping in the next page. s5b_winners.py then distils the common sections the field tends to cover, the confirmed format, and the gaps we can own — the sub-topics winners treat thinly, which is where our angle lives.

"Cited by AI?" shows up twice — on purpose
The SERP snapshot reports whether Testlify is cited in Google's AI Overview (Step 4). The AI-answer check (Step 6) reports whether Testlify is cited by AI assistants (a different surface). Two separate places AI answers questions, both worth knowing — each is labelled so the reader isn't confused.

08Step 6 — the AI-answer check, gated on both sides

The API endpoint for this (llm_mentions) takes only a keyword and sorts by popularity. So an ambiguous word — "recruiting" means HR to us, college sports to the world — returns the biggest meaning, not ours. We wrap the call with an AI gate on each side.

A

Gate in — pick a query that can't drift

Before the call, an AI picks a disambiguated query (e.g. "recruiting metrics" instead of bare "recruiting"). After ~3 failed attempts it gives up cleanly rather than force a bad pull. Driven by s6_flow.py.

B

The call paid

s6_aeo.py asks the API what AI answers for that query, which domains it cites, and whether Testlify is among them (a GEO gap if not), plus the sub-questions AI splits the topic into.

C

Gate out — is this actually our topic?

After the call, an AI judges the results against the topic. Off-topic drift is reported honestly as "no usable signal" — the step stands alone and never borrows from another step to look fuller than it is.

A null result is a real result
On many B2B topics this step legitimately finds no clean AI-answer signal. That's recorded as-is and carried into the brief untouched — never backfilled or faked. Honesty over a tidy-looking output.

09Built to run unattended — the safety mechanics

Because this runs on a schedule with no human watching, three mechanisms make sure a stop, a crash, or an empty wallet never corrupts a run or wastes money.

↩️

Resumable

Every step writes a named file; on re-run a finished step is skipped and its output reused. A crash resumes where it stopped and never repeats a paid call. --redo or --from N force a rerun.

💳

Credit pre-flight

Before spending, the orchestrator reads the live DataForSEO balance. If it's below the buffer (~$1), it stops cleanly having spent nothing and leaves the topic in the queue — so it resumes automatically after top-up.

🧷

Atomic writes

Every save writes to a temp file, then renames it over the target in one move. So a file's existence guarantees it's complete — a crash mid-write leaves only a stray temp file (ignored), never a half-written output that resume would trust.

Where the credentials live
The only secret the engine needs — the DataForSEO login + API password — sits in a local scripts/.env (locked down, never committed), read only by dfs.py. The AI steps need no key at all; they run on a headless Claude or Codex CLI.
