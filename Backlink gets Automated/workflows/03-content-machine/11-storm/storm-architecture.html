Content Machine · Research Phase

How STORM researches a topic

STORM is our deep-research engine. It works like a small newsroom: it invents a few expert interviewers, runs a separate grounded interview for each, and writes a fully-sourced research document from everything they gather. We wrapped the STORM engine so it runs on a headless CLI — our Claude subscription or Codex — and reads whole articles instead of blurbs. Here is exactly how it works, script by script.

01The one idea

STORM does not "ask an AI to write an article." It runs a research operation: it hires interviewers, each interviews an expert who may only speak from sources it just read, and only then does it write — with a citation on every claim.

🧭

1. Invent the interviewers

A few "editors," each with a different angle, so the topic is researched from several viewpoints at once.

🎙️

2. Run a grounded interview each

Every editor holds its own interview with an expert that answers only from articles it pulls off the web in real time.

🗂️

3. Build an outline

From everything the interviews surfaced, it drafts the document's section structure.

✍️

4. Write, fully sourced

It writes each section from the gathered evidence — every sentence backed by a source it actually read.

The one rule that governs everything
Every sentence is grounded in a scraped source, and the output is evidence — never the finished article. STORM answers only from what it actually read. Its result is a dossier — raw, cited research our writer builds from. If a claim can't point to a source STORM scraped, it doesn't belong.

02The words you need first

A handful of terms run through the whole engine. Here they are in plain language, once.

Dossier — the thing STORM produces: a long research write-up with a real source behind every claim. It is not the finished article; it's the raw evidence our writer draws from.
Grounded / cited — every sentence points to an actual web page STORM read. Nothing comes from the AI's own memory, so it can't quietly make things up.
Perspective (editor / persona) — an invented interviewer with one angle (say, cost, or how it's measured). It's the --perspectives knob: more perspectives = more angles the topic gets researched from.
The bridge (shim) — a small relay we run on our own machine that makes STORM send its AI calls to a headless CLI instead of a paid AI service. It forwards to whichever provider you pick — Claude (default) or Codex, both on our own subscription, no API key. This is why the AI part costs $0.
The retriever (scraper) — the part that finds web links and then reads the whole article behind each one, not just the one-line search blurb.
RAG — "retrieve, then write": for each section, find the most relevant source passages first, then write only from them. It's what keeps the writing tied to real evidence.

Gotcha we fixed — finding the engine after a folder rename
The STORM engine (knowledge_storm) isn't installed like a normal library — it's loaded straight from the local ./engine source next to the scripts.
  • What broke: the way Python found it was a file (_storm_local.pth) holding a hard-coded absolute path to the old 02-content-machine folder. When we renumbered the layer 02 → 03, that path went dead and the run crashed with ModuleNotFoundError: knowledge_storm — even though the code sat right there.
  • The durable fix: run_storm.py now works out where ./engine is from its own file location and adds it to Python's search path before importing the engine. So a rename or fresh checkout can never orphan it again.
Why it costs almost nothing
All the AI runs free through the bridge on our subscription. The only thing that costs money is the web-search lookups in the retriever — about $0.10–$0.20 per topic. Reading the full articles is free.
Gotcha — the bridge's opening note is worded carefully on purpose
The bridge prepends one short line to every prompt telling the model to reply with just the answer (no "Here is" opener, no sign-off). It is phrased as a plain formatting note, never as a "SYSTEM:" instruction — because when it read like a system directive, the model's prompt-injection defence treated our own long inputs as an attack and refused, returning empty answers. The mild wording is load-bearing, not cosmetic.

04The full pipeline — steps 0 to 7

One command runs the research chain (Steps 1–5); two small extras render the log and the viewable page. Every file lands under out/<topic>/. Only Step 2 spends money (the web search); all the AI is free via the bridge. Sections 05–10 zoom into the parts that matter most.

Get ready no file yet

Two quick bits of setup — nothing is written yet.

  • Start the bridge (shim.py) so STORM's AI calls run on a headless CLI — Claude or Codex, free.
  • Pick the provider with --provider claude|codex (and an optional --model); run_storm.py hands both to the bridge.
  • Set the knobs in run_storm.py: perspectives (editors), turns (questions each), topk (links per search). The automated run uses 3 perspectives × 3 turns.
1

Decide the editors (personas)

How they're decided: an AI names a handful of sub-topics around the theme, then turns each into an "editor" — an interviewer with one distinct angle (cost, methodology, and so on) — plus one plain fact-checker. The number of editors is a knob you set; more editors = more angles covered.

  • persona_generator.py — writes the editor list.
↓ §05 — how each editor then gets its own interview
2

Run the interviews the research — every fact is gathered here search $

Each editor interviews a grounded "expert," one question at a time. Four files do the work — two that run it, two that record it:

  • knowledge_curation.py — runs the interview loop: the editor asks a question; the expert answers using only what was just read.
  • dataforseo_rm.py — the retriever: for each question it searches the web, then reads the pages it finds.
  • conversation_log.json — records every question, its answer, and the exact sources behind that answer.
  • raw_search_results.json — the shared pool: all the source text gathered across every interview.
What the pool actually stores — not whole articles
Each page the retriever reads is sliced into ~1,200-character chunks (up to ~14 per page); only those chunks are saved into the pool, never the full page. So a source lives in the pool as a set of passages, and the interview log points to the chunks behind each answer — not the entire article.
↓ §06 — the turn-by-turn loop ↓ §08 — how it reads pages deeply
3

Build the outline

What "from what the interviews surfaced" means: an AI reads all the interview Q&A and groups the recurring themes into headings — a rough first outline, then a refined one. It's built from the questions and answers, not from a template.

  • outline_generation.py — writes both outline passes → storm_gen_outline.txt.
  • Note: this is STORM's own research scaffolding. Our article's real structure comes from the DataForSEO brief later — STORM's outline is never published.
4

Write the sections

How the evidence is pulled: for each heading, STORM searches the pool by meaning and keeps the few chunks that match best, then writes the section from just those — every sentence cited. No new web searches; it only uses chunks already in the pool from Step 2.

  • storm_dataclass.py — finds the best-matching chunks for each heading.
  • article_generation.py — writes the cited section from those chunks.
  • storm_gen_article.txt — the drafted dossier.
  • url_to_info.json — the cited-source map: which chunks each source contributed, with its citation number.
↓ §09 — matching evidence to headings
5

Polish & finish

Add a short summary on top; the section bodies pass through unchanged (no trimming).

  • article_polish.py → storm_gen_article_polished.txt — the dossier the write phase receives.
6

Render the step log optional

Turn the raw record of every AI call into a readable trace of what STORM did — for auditing a run.

  • build_steplog.py → STEP-LOG.md.
7

Render the viewable page optional

Render the dossier as one shareable web page — citations clickable, a numbered references list, a contents sidebar. Read-only; it never changes the research.

05From editors to interviews — the setup

Once the editors exist (Step 1, by persona_generator.py), here is what actually happens before and around the questions.

Each editor gets its own interview

Every editor (persona) is handed a fresh, empty interview. An "interview" isn't a document — it's just a conversation that grows one turn at a time. It starts with nothing in it.

They all run at the same time

The interviews don't happen one after another — they run in parallel (a few at once), and they are completely independent. Editor A never sees Editor B's conversation. That independence is exactly what creates breadth: each editor chases its own angle without being influenced by the others.

How the very first question is born
Because the interview starts empty, there's no conversation to build on yet — so the editor generates its first question purely from the topic + its own angle. (e.g. the "cost" editor opens with a cost question, the "methodology" editor opens with a how-is-this-measured question.) Every later question is built on the answers so far — that's the loop in the next section.
Our upgrade — more angles, not more Wikipedia
Want broader research? Add editors (raise the persona count), not questions. Note: the engine tries to read related Wikipedia contents pages as light inspiration for the personas — but that's optional, so even when it's blocked the editors still come out strong and varied.

06Inside one interview — the loop

One interview is the same three-part turn, repeated. Two AI roles play it: the Asker (the editor) and the Answerer (the grounded expert, run by knowledge_curation.py). Here is a single turn, in order.

A

The Asker asks one question

It looks at the topic, its own angle, and the conversation so far, and writes one question — the most useful thing to learn next.

B

The Answerer researches & replies

It never answers from memory. For that one question it does four things (steps 1–3 are the retriever, dataforseo_rm.py):

1turn the question into Google searches→ 2find the links→ 3scrape the full articles→ 4write an answer, every sentence cited
C

The turn is saved to the conversation

The question, the grounded answer, and the exact sources behind it are bundled into one "turn" and added to the conversation. The conversation just grew by one.

lands inconversation_log.json
↻

Repeat — building on the last answers

Back to the Asker. Now it can see what it just learned, so its next question builds on the previous answers instead of repeating them. It keeps going until it feels the topic is covered.

Our upgrade — the "ask at least 3" floor
With full-article answers, an editor tends to feel "done" after just one or two questions — which starves the research. So we nudge every editor to ask at least three questions before it's allowed to wrap up. That's what keeps each interview deep and the range of sources wide.

07Who sees what — the memory model

The two roles have very different memory, and it's deliberate. This is what keeps the research honest instead of drifting into invention.

🧑‍💼

The Asker (editor)

has short-term memory — to choose a good next question
Remembers
the last few answers in full. Older ones are compressed to just "you asked about X" (answer stripped out), so it never carries the whole transcript.
🔬

The Answerer (expert)

has no memory — fresh on every question
Forgets everything
a brand-new call each time. It sees only the current question — never earlier questions, never earlier answers. A goldfish, on purpose.
↔️

Between the two roles

Almost nothing passes. The Asker never sees the Answerer's raw sources — only its finished answer. Two minds passing notes.

⏭️

Between two questions

Only answers carry forward, and only to the Asker. The Answerer restarts from zero every question.

👥

Between the editors

Nothing at all — separate, parallel interviews. Their isolation is what creates breadth.

Why so much forgetting?
A memoryless expert can't hallucinate its way forward — with nothing to lean on, it's forced back to real sources for every single answer. The only "memory" in the entire system is the short window the Asker uses to ask a smart next question. Every fact comes from a freshly-read page.

08How it reads the web — deep, not shallow

Most tools like this only skim the one-line blurb under a search result. Ours — the retriever, dataforseo_rm.py — reads the whole article. This is the swap that makes STORM's evidence specific instead of generic.

📄

Shallow — STORM's default

reads the ~150-character search blurb

Fast, but thin and generic — the same headline stats everyone else already quotes. This is the built-in retriever we replaced.

📚

Deep — what we built

finds the link, then reads the whole article

We use search only to find the links, then fetch and read the full article body ourselves — the specific, segmented detail nobody else surfaces. The scraping is free.

09How the document is written

The writing step (Step 4) does not touch the web again. It writes entirely from the pool of evidence the interviews already gathered — matching evidence to headings is "RAG" (§02).

🔎

Match evidence to each heading

For a section, storm_dataclass.py searches the pool by meaning (not keywords) and pulls the top 8 chunks most relevant to that heading.

✍️

Write it dense and cited

article_generation.py writes the section from those chunks — told to favour concrete specifics (numbers, ranges, dates) and to cite every claim. Length follows the evidence; no padding.

🧾

Summarize & finish

A short lead goes on top (Step 5), and the finished dossier is saved.

A funnel, not waste
Only the strongest sources make the cut — roughly 40% of everything gathered gets cited. The rest stays in the pool as backup. That's intentional: gather wide, then keep only the most relevant material per section.

Where each run lands — pillars flat, spokes nested
Where the output folder sits depends on the optional --hub flag:
  • A pillar (main article) has no hub — its run lands flat at storm/out/<TopicDir>/.
  • A spoke passes --hub <pillar-slug> — its run nests one level down at storm/out/<hub>/<TopicDir>/, so every spoke sits under its pillar.
  • The research conductor drives this: it works out the hub once from the spoke's spoke-of: source and calls config.storm_dir(topic, hub), which mirrors the same layout so it can find the dossier again.
Where STORM sits in the bigger machine
STORM is the Evidence Engine of the research phase. Alongside the DataForSEO brief (keywords + SERP + the competitor map), it hands the writing phase everything it needs — so the writer just writes, and never has to go hunting for a fact, a stat, or a source.
