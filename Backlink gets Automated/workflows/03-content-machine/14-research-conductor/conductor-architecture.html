Content Machine · Research Phase

How the research conductor runs the whole phase, hands-off

The four earlier engines each do one job. The conductor is the thing that runs them in order, unattended: it picks one topic, threads that topic's identity through DataForSEO → STORM → gap-check → research-structure, checks each result, flags when we already rank for the keyword, packages a write-ready bundle, then mints and vets this hub's follow-up topics (its spokes). You launch it with one command — /research — pick a provider (Claude or Codex) and model, and walk away. One topic, no human in the loop. Here is exactly how it works.

01The one idea

Each research engine already works on its own. What was missing was a single, reliable way to run all of them for one topic without a person babysitting the handoffs. That's the conductor — it invents nothing, it just sequences, checks, and packages.

🎯

1. Pick

Choose the next topic — from the queue, or the idea cabinet if the queue is empty — and lock its identity.

🔗

2. Sequence

Run all four engines in order, passing the topic's identity through each so every output lands together.

🛡️

3. Guard

Check each engine's output before the next one uses it — a dud STORM run stops the whole thing; a no-demand topic skips gracefully.

📦

4. Package & grow

Bundle the result for the writer, flag any cannibalisation, mark the topic done, then mint + vet this hub's spokes.

The one rule that governs everything
The slug is the thread. The conductor picks one topic and mints a short nickname — its slug — then passes that same slug + title + angle to every engine, and every engine writes its output under that one slug. That single shared thread is what lets four separate tools behave like one pipeline (and what makes a crash resumable). A spoke also carries its pillar's slug, so a spoke's output nests under its hub everywhere.

02The words you need first

The conductor pulls together the whole phase, so a few coordination terms matter. Plain language, once.

The conductor — the top-level command (run_research.py) that runs the whole research phase for one topic by calling the four engines in order. It sequences; it doesn't think.
The queue (research-log.csv) — the to-do sheet: one row per topic with its status. The single source of truth for what's done and what's next.
The idea cabinet (clubbed-ideas.csv) — where topics come from: title, angle, competitor URLs, reuse verdict. The source of truth for idea data (never edited by the conductor).
Slug — the short nickname minted from a topic's title. It's the thread that ties every engine's output together under one folder name.
Hub vs spoke — a hub is a main topic from the cabinet; a spoke is a sub-topic it spawns (its own future article), queued right after its hub and nested under it.
Primary keyword — the one search phrase DataForSEO picks as the article's main target. It's what STORM researches, and what the cannibalisation flag looks up.
Cannibalisation flag — a warning (never a block) that we already rank on page 1 for this article's keyword, so a second page could split our own traffic. Decided once, shown in the bundle.
Reuse verdict — the "do we already have content like this?" answer: Already have it · Improve existing · Build from parts · Brand new. Every idea (and every minted spoke) carries one.
Word band — the target article length. DataForSEO reads the live search results for the keyword and reports the range of lengths of the pages currently ranking (e.g. 3,000–4,000 words).
The bundle — the final handoff: one folder holding the blueprint plus pointers to everything else the writer needs.
Resumable — a step is skipped if its output already exists, so a crash (or a usage-limit stop) picks up where it left off instead of repeating expensive work.

03The queue — how a topic gets chosen

Everything is pull-based: the conductor does exactly one topic per run and pulls the next one itself. There are no triggers or push-events — a scheduler just fires the same command repeatedly, and the queue decides what happens each time.

The pick order (every run)

  1. Take the next unfinished row in the queue — pending, or in_progress (reclaimed; see below).
  2. Because spokes sit right after their hub, a cluster is researched depth-first: the hub, then its spokes, then the next hub.
  3. If the queue has nothing unfinished, pull the next eligible idea from the cabinet and add it as a new row. Writable ideas are pulled in priority order — Brand new / Build from parts first, then Improve existing last. A Tool escalation idea is dropped in as a terminal tool-build marker (a human builds it) and never picked for writing.

The row's life — the status values

research_statusMeaning
pendingQueued, not started.
in_progressA run started it. Reclaimed on the next run if it crashed.
doneResearch finished; the bundle is ready for the writer.
skippedTerminal. No keyword demand — an editorial/niche topic; a remarks note explains it. ↓ §06
failedTerminal. Hit the attempts cap (MAX_ATTEMPTS = 3) — dead-lettered so a broken topic can't block the queue forever.
tool-buildTerminal. Needs a tool built, not an article written.
Why "in_progress" gets reclaimed, not skipped
A row left in_progress means a previous run started that topic but crashed before finishing. Since runs are strictly one-topic-at-a-time, that row is never a live parallel run — so the next run retries it instead of orphaning it (up to MAX_ATTEMPTS). Combined with the slug thread, that's what makes an interrupted run safe to simply re-fire.

The entry point — the /research command
You launch a run by typing /research. It first asks two things: which provider to run every LLM step on — the locally authenticated Claude CLI (default) or the Codex CLI — and which model (or the CLI's default). It then runs the whole chain on that choice. Both providers are headless and need no API key; under the hood the command passes your picks as --provider / --model to the conductor, which threads them to every engine and to STORM's bridge.

06Crash-safety, and the exits that don't crash

Because this runs unattended and each engine is expensive, three things matter most: it must resume cleanly, it must never carry a bad STORM result forward, and a dead-end topic must bow out gracefully instead of jamming the queue.

How resume works

  • The slug is the thread — every engine writes under out/<hub>/<slug>/, so resume is just "does this step's output file already exist?" If yes, skip it.
  • Safe to Ctrl-C: the topic stays in_progress and the next run reclaims it.
  • Flags to override: --redo reruns everything, --from N forces a rerun from step N, --until N stops after a step (e.g. --until 2 stops after STORM).
Gate 1 — STORM: the one place it refuses to continue
STORM can exit "successfully" yet return an empty or stub article (~300 words instead of a healthy ~9,000) when its write step transiently fails. The conductor checks the word count: below 1,500 words (STORM_MIN_WORDS) it retries STORM once, then fails the whole run loudly rather than proceed.
Why stop instead of limp on: a stub dossier produces almost no evidence cards, so our own pages dominate the blueprint and the citations come out nearly all our own site. A failed run is treated exactly like an error — better to stop and retry than poison everything downstream.
Graceful exit — the no-keyword-demand skip
Some topics are editorial: no search phrase has real volume. DataForSEO's scorer refuses (it won't invent a keyword), exits code 3, and the conductor catches it as a soft outcome — it marks the topic terminal skipped with a remarks note, then returns cleanly. The queue is never crashed or retried; the next run just picks the next topic.
Real example: "Why Candidates Still Abandon Job Applications in 2026" → DataForSEO found 16 keywords, max volume 70, none clearing the floor → row marked skipped, remark: "no keyword demand — no keyword cleared the volume floor (editorial/niche topic, not researched)."
Graceful exit — the attempts cap
A topic that fails the same way every run would be reclaimed forever, burning paid API calls each time. After 3 attempts (MAX_ATTEMPTS) the row is marked terminal failed and skipped, so one broken topic can never block the whole queue.

07The cannibalisation flag — "do we already rank for this?"

Before we spend on a full STORM run, one cheap check: are we about to write a page that competes with a page we already have? If we already rank on page 1 for the keyword, a second page can split our own traffic. The flag warns the team — it never stops the build.

📊

The data it uses

already paid for, in the foundation layer
Our real ranking footprint
Not a fresh lookup — it reuses 00-foundation's ranked_keywords pull (traffic-raw.json, ~18k rows: every keyword our domain ranks for + position + URL). It builds a slim keyword → [rank, url] lookup once (~13k unique keywords, cached as our-rankings.json, keeping our best position per keyword).
⚖️

How it decides

exact match, page-1 only
The rule
Look up the primary keyword. Flag it only if we rank in the top CANNIB_RANK_MAX = 10 (page 1) — that's where a second page actually splits our traffic; a #40 nobody sees is not real cannibalisation. It's a true-negative-safe check: it fires only on a real page-1 ranking. Off-switch CANNIB_CHECK = 0; fails open if the footprint file is missing.

Worked example — real run (Sonnet 5)

The hub topic's primary keyword was "cost per hire". The flag looked it up in our footprint:

KeywordOur best rank≤ 10 (page 1)?Result
cost per hire #91
via testlify.com/hr-glossary/cost-per-hire-cph/		 no — page 10 NOT flagged. We rank so deep nobody sees it, so a new page doesn't split real traffic. The row's cannibalization stays blank; the build proceeds normally.
The other side (illustrative): had that same keyword sat at #4, the check would have written cannibalization = "#4 · cost per hire" + the URL onto the row, and the bundle would carry a TEAM SHOULD KNOW warning: build anyway, but this article must clearly outperform that page.
Decided once, carried forward
The verdict is written to the queue row a single time, here in Step 1b — never re-decided downstream. The bundle just reads it. That's the single-source-of-truth rule: one place owns the flag, everything else points at it.

The word target — one authority, chosen once

Two sources can disagree on how long the article should be, so the bundle picks one authority:

  • Clubbed target_words — a coarse, cluster-wide asset-engine estimate (the median length of ranking pages, taken once).
  • DataForSEO's live-SERP Word band — computed per topic from the pages actually ranking for this keyword, the day we researched it.

DataForSEO wins — it read this keyword's current search results. bundle.py's _dfs_word_band parses the band from the brief and surfaces that as the target; it falls back to the clubbed median only if the brief has no band.

09Spokes — from bare keyword to vetted idea, and where it all sits

One run does one topic — but when a hub finishes, it grows the queue with its follow-up topics. The catch: DataForSEO hands back spoke candidates as bare keywords, and a bare keyword isn't a real idea. So Step 6 turns each one into a proper, reuse-checked idea before it enters the pipeline.

The three moves per spoke keyword

1 Mint
→
2 Reuse-check
→
3 Re-angle if duplicate
  • Mint (spoke_idea.mint) — the LLM writes a real title + angle from the bare keyword, its pillar hub, and the brand.
  • Reuse-check (reuse_one.check) — a proper semantic check, not a string match. It vectorises the idea with Voyage embeddings (voyage-4-large), finds the 40 nearest existing pages from the content-index, reranks them (rerank-2.5), keeps the top 6, and hands them to the same reuse-judge the asset engine uses. Out comes a real verdict: Already have it · Improve existing · Build from parts · Brand new.
  • Re-angle if duplicate — only Already have it triggers a redo: the loop re-mints a sharper, genuinely different angle, up to 3 tries. The other three verdicts all proceed.
Needs Voyage — but never at the hub's expense
Minting + the reuse check need a VOYAGE_API_KEY (a paid embedding call). This whole Step 6 spoke enqueue runs after the hub is already marked done, wrapped in try/except — so if Voyage is absent or errors, the hub still finishes cleanly and the spokes are simply skipped, not lost work.

Spokes make it recurring — but bounded, and nested

  • Ranked, top 3 only. DataForSEO scores every spoke candidate (0.5·relevance + 0.25·volume + 0.25·ease) and the conductor keeps only the top 3 (MAX_SPOKES).
  • One level only. A spoke never spawns its own spokes. Without this, each spoke would generate 3 more (3 + 9 + 27…) with no bound — so each hub yields at most 3 spokes, full stop.
  • Nested under the pillar everywhere. A spoke's output sits under its hub in every engine directory — dataforseo/ · gap-check/ · storm/ · research-structure/ · research-bundle/ — via the --hub arg the conductor computes once from the spoke's spoke-of: source. Hubs stay flat.

Where the conductor sits in the bigger machine
The conductor is the top of the research phase — the single entry point that drives all four engines and ends at the write-ready bundle. From there, /write picks up any topic whose research is done and turns the bundle into the finished article. Research is fully hands-off; the writer never has to gather anything.
