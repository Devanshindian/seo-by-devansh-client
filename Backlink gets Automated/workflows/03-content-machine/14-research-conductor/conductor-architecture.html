Content Machine · Research Phase

How the research conductor runs the whole phase, hands-off

The four earlier engines each do one job. The conductor is the thing that runs them in order, unattended: it picks one topic, threads that topic's identity through DataForSEO → STORM → gap-check → research-structure, checks each result, then packages a write-ready bundle and queues the topic's follow-ups. You launch it with one command — /research — pick a provider (Claude or Codex) and model, and walk away. One topic, no human in the loop. Here is exactly how it works.

01The one idea

Each research engine already works on its own. What was missing was a single, reliable way to run all of them for one topic without a person babysitting the handoffs. That's the conductor — it invents nothing, it just sequences.

🎯

1. Pick

Choose the next topic — from the queue, or the idea cabinet if the queue is empty — and lock its identity.

🔗

2. Sequence

Run all four engines in order, passing the topic's identity through each so every output lands together.

🛡️

3. Guard

Check each engine's output before the next one uses it — a dud STORM run stops the whole thing.

📦

4. Package & queue

Bundle the result for the writer, mark the topic done, and queue its spokes.

The one rule that governs everything
The slug is the thread. The conductor picks one topic and mints a short nickname — its slug — then passes that same slug + title + angle to every engine, and every engine writes its output under that one slug. That single shared thread is what lets four separate tools behave like one pipeline (and what makes a crash resumable).

02The words you need first

The conductor pulls together the whole phase, so a few coordination terms matter. Plain language, once.

The conductor — the top-level command (run_research.py) that runs the whole research phase for one topic by calling the four engines in order. It sequences; it doesn't think.
The queue (research-log.csv) — the to-do sheet: one row per topic with its status. The single source of truth for what's done and what's next.
The idea cabinet (clubbed-ideas.csv) — where topics come from: title, angle, competitor URLs. The source of truth for idea data (never edited by the conductor).
Slug — the short nickname minted from a topic's title. It's the thread that ties every engine's output together under one folder name.
Hub vs spoke — a hub is a main topic from the cabinet; a spoke is a sub-topic it spawns (its own future article), queued right after its hub.
The bundle — the final handoff: one folder holding the blueprint plus pointers to everything else the writer needs.
Resumable — a step is skipped if its output already exists, so a crash (or a usage-limit stop) picks up where it left off instead of repeating expensive work.

03The queue — how a topic gets chosen

Everything is pull-based: the conductor does exactly one topic per run and pulls the next one itself. There are no triggers or push-events — a scheduler just fires the same command repeatedly, and the queue decides what happens each time.

✅

The queue

research-log.csv · status only
Tracks progress
One row per topic: slug · asset · angle · source · research_status · write_status · dates. The conductor reads and writes this to know what's done and what's next.
🗄️

The idea cabinet

clubbed-ideas.csv · idea data only
Supplies topics
Title, angle, proof URLs, reuse verdict. Read-only to the conductor — the competitor URLs and the like are looked up live by matching the title, never copied into the queue.

The pick order (every run)

  1. Take the next unfinished row in the queue — pending, or in_progress (reclaimed; see below).
  2. Because spokes sit right after their hub, a cluster is researched depth-first: the hub, then its spokes, then the next hub.
  3. If the queue has nothing unfinished, pull the next eligible idea from the cabinet (reuse verdict = "Brand new" or "Build from parts") and add it as a new row.
Why "in_progress" gets reclaimed, not skipped
A row left in_progress means a previous run started that topic but crashed before finishing. Since runs are strictly one-topic-at-a-time, that row is never a live parallel run — so the next run retries it instead of orphaning it. Combined with the slug thread, that's what makes an interrupted run safe to simply re-fire.

The entry point — the /research command
You launch a run by typing /research. It first asks two things: which provider to run every LLM step on — the locally authenticated Claude CLI (default) or the Codex CLI — and which model (or the CLI's default). It then runs the whole chain on that choice. Both providers are headless and need no API key; under the hood the command just passes your picks as --provider / --model to the conductor (and to STORM's bridge).

06Crash-safety and the one hard gate

Because this runs unattended and each engine is expensive, two things matter most: it must resume cleanly, and it must never carry a bad STORM result forward.

How resume works

  • The slug is the thread — every engine writes under out/<slug>/, so resume is just "does this step's output file already exist?" If yes, skip it.
  • Safe to Ctrl-C: the topic stays in_progress and the next run reclaims it.
  • Flags to override: --redo reruns everything, --from N forces a rerun from step N, --until N stops after a step (e.g. --until 2 stops after STORM).
The STORM gate — the one place it refuses to continue
STORM can exit "successfully" yet return an empty or stub article (~300 words instead of a healthy ~9,000) when its write step transiently fails. The conductor checks the word count: below 1,500 words it retries STORM once, then fails the whole run loudly rather than proceed.
Why stop instead of limp on: a stub dossier produces almost no evidence cards, so our own pages dominate the blueprint and the citations come out nearly all our own site. A failed run is treated exactly like an error — better to stop and retry than poison everything downstream.

The brand constants
Voice, style, product facts, the SEO checklist, and the rest are pointed to, not copied — so there's one source of truth and no drift between topics.

The cover sheet (bundle-<slug>.md) opens with the topic's title, its picked reader persona (reused from the blueprint, where it was decided once) and its author byline (picked here), then lays out ten numbered divisions — Division 1 is the plan (WHAT to write), 2–10 are the HOW:

Spokes make it recurring — but bounded

When a hub finishes, its spoke candidates (their own future articles) are inserted right after it in the queue. So the next few runs research those spokes before moving to a brand-new hub — the cluster is worked depth-first, and one command fired on a schedule steadily clears the backlog.

But not every candidate, and not forever. Two limits keep it sane:

  • Ranked, top 3 only. DataForSEO scores every spoke candidate — 0.5·relevance + 0.25·volume + 0.25·ease — and the conductor enqueues only the top 3 (config.MAX_SPOKES). There's also a hard floor: any candidate whose cluster-relevance is ≤2 is dropped outright, so a huge but off-topic head like "benchmarking" (110k volume) can never sneak in on volume alone.
  • One level only. A spoke never spawns its own spokes. Without this, each spoke would generate 3 more — 3 + 9 + 27… with no bound; capping breadth alone wouldn't fix it. So each hub yields at most 3 spokes, full stop.
Where the conductor sits in the bigger machine
The conductor is the top of the research phase — the single entry point that drives all four engines and ends at the write-ready bundle. From there, /write picks up any topic whose research is done and turns the bundle into the finished article. Research is fully hands-off; the writer never has to gather anything.
