Asset Engine · Method 5

Reuse Check — do we already have this asset?

Before building anything, every idea in the merged pool is checked against the company's existing content. A semantic search (RAG) finds the closest pages; an LLM reads them and decides whether to build brand-new, build-from-parts, improve an existing page, or that we already have it. Here's exactly how it works, script by script — and why the same logic now vets research spokes too.

01The one idea

Two payoffs, in one check: don't rebuild something we already own, and don't research from scratch when related pages can be reused as raw material.

🧭

Find the neighbours

Turn the idea into meaning-numbers and pull the closest existing pages by meaning, not keyword overlap. This is the "RAG" step.

🔁

Rerank for precision

A second model re-reads the top 40 pages against the idea and keeps the genuinely relevant 15.

🧑‍⚖️

Read & judge

An LLM reads the top candidates' full text and returns exactly one of four verdicts, plus its reasoning.

🧠

One shared brain

The same retrieve-then-judge logic now also vets research spokes — one reuse brain, two callers.

The one rule

The read decides, not the score — and the verdict is decided exactly once.

  • Retrieval only shortlists ("these look similar"). It never decides build-vs-reuse.
  • The judging LLM is handed the candidates' full text only, never the match scores — so the verdict comes purely from reading and the score can't bias it.
  • The verdict is written once, in Stage 3, and carried forward — never re-decided in a later step.
Inputs
  • clubbed-ideas.csv — the merged pool from all three idea methods (from 4-merge), with its six reuse columns empty.
  • content-database.csv — every existing page, and it must carry the Full content column (from 00-foundation/1-site-catalogue). Only pages with real body text can be reuse candidates.

02The words you need first

Five terms this page leans on. Each defined once, in plain language, then used the same way throughout.

Embedding — text turned into "meaning-numbers" (a long list of numbers, a vector). Two pieces of text that mean similar things get similar numbers, so "closeness in meaning" becomes "closeness of numbers" a computer can measure. We use Voyage's voyage-4-large model.
Content-index — every existing page embedded ahead of time and saved to disk, so search is instant. Built once per company and only refreshed when the content database changes. Each page is stored as two vectors: one for its title, one for its body.
RAG (retrieval-augmented generation) — find the most relevant existing pages first, then hand that real text to the LLM, so it judges from what we actually own rather than from memory.
Rerank (a "cross-encoder") — a second model (rerank-2.5) that reads the query and a candidate page together and scores true relevance far better than raw vector distance. Vector search casts a wide net cheaply; the reranker does the precision work.
Blended dense score — how the two vectors combine into one ranking: score = α·(query↔title) + (1−α)·(best query↔body chunk), with α = 0.5. Splitting title from body stops a long article's body from drowning out its title signal.
Two different "titles" — don't confuse them

The page Title (from content-database.csv) is what we embed into the index in Stage 1. The Asset title (the idea's name, the Asset column) is the search query in Stage 2. Same word, opposite sides of the search.

The full text of every page already lives in content-database.csv. Storing ~15–40 full pages per idea would balloon the file to tens of MB for nothing, so the clubbed sheet keeps only links. Two hands: mechanical code vs. the judging LLM

⚙️

Mechanical

code + a free-tier API — deterministic, repeatable
Does
  • Builds the two-vector content-index (Voyage embeddings).
  • Blended dense retrieve → rerank-2.5 → top 15.
  • Deterministic topic catalogue (keyword match, no AI).
  • Enforces Chosen links ⊆ candidates — drops any invented URL.
🧑‍⚖️

Judgment

the LLM — reads and decides
Decides
  • Reads the top candidates' full text.
  • Runs three tests (topic · format · angle) on each.
  • Picks exactly one of the four verdicts.
  • Writes the Why — evidence, not the score.

04The full pipeline

Three stages across two step scripts. The orchestrator runs them in order and each writes its columns before the next reads them.

Phase 1 · Index (once per company)
1

Build the two-vector content-indexfree APIcode

Every page with real body text is embedded twice — once from its title alone (one clean fingerprint), once from its body (chunked for long pages). Splitting them stops a long body from drowning out the title signal (the v1 failure). Built once; refreshed only on content change.

  • step_1_retrieve.py · voyage.py → writes _work/content-index/title/ + _work/content-index/body/ (resumable, atomic .npy saves)
  • ↓ 05 — the retrieval, in detail
Phase 2 · Retrieve (per idea, in parallel)
2

Blended retrieve → rerank → top 15free APIcode

For each idea, the query = its Asset title only (angle and parentheticals stripped). Embed it, take the top 40 pages by blended dense score, then rerank those 40 with rerank-2.5 and keep the 15 genuinely relevant ones. Runs 8 ideas in parallel.

  • step_1_retrieve.py → writes the RAG candidates column
  • ↓ 05 — the 40→15 funnel + settled config
3

The topic catalogue — smart label, dumb matchLLM labelcode match

A precision tool (RAG) can't guarantee completeness, so a second, deterministic column lists every page on the topic. One LLM pass tags each asset with 1–3 distinctive keywords; a keyword matcher (light stemming, foreign-language pages excluded, over-generic keywords dropped) then lists every English page whose title/URL contains one.

  • step_1_retrieve.py · topic-keywords.md → writes Topic pages we own + Reference links (the de-duped union)
Phase 3 · Judge (per idea, in parallel)
4

LLM verdict per ideaLLM · free CLI

Each idea is judged against the top 7 of its RAG candidates. Their page text is not stored in the sheet — it's fetched on demand by URL from content-database.csv and pasted into the judge prompt. The LLM runs three tests and returns one verdict, the links, and why. 6 judges run at once; an unparseable reply is re-asked, then left for resume.

  • step_2_judge.py · reuse-judge.md → writes Reuse verdict · Chosen links · Why
  • ↓ 06 — the four verdicts + the three tests
Resumable by design

The clubbed CSV is edited in place, so it can't double as the resume marker. Instead each step drops a sentinel (.stage2-retrieved.done, .stage3-judged.done) and both steps are internally resumable too — the index tracks its own state, retrieved rows are skipped, and every landed verdict is appended to reuse-judge-results.jsonl. A crash resumes without repeating a paid embed or a judged idea.

Why the title-only query

The Distinct angle is a competitor-gap / workflow-note paragraph — appending it drags the search toward tangents. Even the title's own parenthetical qualifier is noise.

  • In testing, keeping "… Benchmark Report (Adoption, AI Cheating, …)" pushed the right page from rank #1 down to #21.
  • Foreign-language duplicates (URLs whose first path segment is an ISO code — /de/, /fr/) are excluded so they don't waste result slots.

What we tested and rejected real — 49-asset eval

Measured on 49 sampled assets against independent LLM relevance labels (2026-06-30). The baseline — full-title query → blended dense top-40 → rerank-2.5 — won every time. Don't re-try these.

Idea triedResultWhy it lost
Best-chunk rerank — feed the reranker the page's winning chunk, not its headworseA pillar page's best passage is an even stronger keyword match, so it promoted broad landing pages and buried focused blogs. Page-head is better.

The one still-open gap

Judges marked ~19 relevant pages per asset; the baseline surfaces ~64% of them at top-15 (recall@15 ≈ 0.64). Since query changes are a proven dead-end, the only lever left for recall is showing more results (top-20/25) — and only if A/B'd on the same 49-asset harness.

06Deep dive — the four verdicts

The judge runs three tests on each candidate, then picks one verdict top-down — first match wins.

The three tests (judged by what you READ, not keyword overlap)
  • Topic test — is the page actually about this asset's subject, not just sharing a word?
  • Format test — same shape? A text article is NOT a calculator / quiz / index / data report / template.
  • Angle test — does it already carry the asset's distinct angle?
VerdictWhen it firesDoesn't count
🟢 Already have it Same topic + same format + already has the angle, at good quality. Building again would just duplicate. Rare — the angle is usually new. Same topic but a text article when the asset is a tool → Improve; same topic but missing the angle → Improve.
🟡 Improve existing ONE page is clearly this same topic but weaker — missing the angle, wrong/old format, thin, outdated. Building means upgrading THAT page. The page already has the angle → Already have it; only scattered bits across pages → Build from parts.
🟠 Build from parts No single page is this asset, but ≥2 candidates each hold reusable material (data, definitions, sections). Build new, reuse the research. One page is basically the asset → Improve; nothing useful → Brand new.
🔴 Brand new No candidate is genuinely relevant — none really covers the topic, or only touches it superficially. Start from scratch. Any candidate that actually covers the topic or feeds the build → Improve / Build from parts.

07The shared reuse brain

This retrieve-then-judge logic is no longer only the asset engine's. The research phase's spoke machinery now calls the exact same brain to vet each new keyword.

When the research conductor mints a spoke (a supporting keyword under a chosen pillar topic), it needs to know the same thing this engine asks: do we already have content like this? Rather than a crude string-match, it reuses this engine's machinery through a single-idea version, 14-research-conductor/scripts/reuse_one.py.

What it shares

Same three pieces, not a re-implementation:

  • The _shared/voyage.py stack (voyage-4-large + rerank-2.5).
  • The same 02 content-index (title vectors of every existing page).
  • The same reuse-judge.md prompt and its four verdicts.

How the spoke uses it

In spoke_idea.py, minting is a small loop:

  • Mint a spoke idea (title + angle) from the keyword.
  • Run reuse_one.check() against existing content.
  • If the verdict is Already have it, re-angle and mint again — up to 3 tries — until it finds a genuinely different angle.
  • Any other verdict (Brand new / Build from parts / Improve existing) proceeds, carrying the real verdict forward.
Where it sits

One reuse brain, two callers. The asset engine (this page) judges ~1,900 ideas in a batch; the spoke pipeline judges one minted keyword at a time with a lighter read window (title vectors only, top 6, 3,000 chars). Same models, same prompt, same verdicts — so "do we already own this?" is answered identically everywhere.

Always ship these two review formats

A self-contained HTML viewer

One offline file with all ideas inline. It:

  • Shows at-a-glance columns; each row expands to the full reasoning and clickable link groups (RAG candidates with scores, Topic pages, Chosen links, Proof URLs).
  • Filters by source method, brand fit, verdict, format.
  • Lets a reviewer mark Keep / Maybe / Cut + notes per idea, exportable to CSV.

A GitHub Pages link

The same HTML published so a reviewer opens one URL, nothing to install.

  • Personal account, randomised non-descriptive repo name.
  • Public repo (free-plan Pages) — treat the URL as trusted-reviewers-only.
  • Taken down when the review window closes.
Always update in place

The viewer is a mandatory output of every run. Once its link is shared, every re-run pushes to the same repo and URL — never a second one. Keep the push clone inside the project (clubbed/output/_pages-repo/), never in /tmp. Record the live URL + repo + clone path so the next session updates the right one.

Where this sits in the bigger machine
  • Upstream — 4-merge hands over the clubbed pool; 00-foundation supplies content-database.csv with Full content.
  • This engine — the last gate before build: it decides, per idea, brand-new vs. build-from-parts vs. improve vs. already-have, and lists the pages to reuse.
  • Downstream — reviewers cut the pool; content creation fetches each idea's Reference links as research; and the research phase's spokes borrow this exact reuse brain.
