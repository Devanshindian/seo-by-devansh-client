Model Other Niches — import formats competitors don't have yet

Many link-bait formats work in any niche — calculators, indices, generators, awards. If a format pulled huge links in finance or real estate but no competitor in our niche has built one, that's a fresh, ownable link magnet. This is a resumable five-step pipeline (run_model_niches.py, no API, no gates) that now obeys the same format-honesty rules as Method 1 — and feeds the merge.

01The one idea

Method 1 finds formats that already work inside our niche. Method 2 finds formats that work elsewhere but haven't arrived here yet — then adapts them to a subject we can credibly own.

Method 1 — Competitor Study

What's working inside the niche

Highest confidence — backed by competitors' real backlink data. Lower novelty.

Method 2 — Model Other Niches

What's working elsewhere but not here yet

Higher novelty — these formats haven't been tried in our niche. Lower certainty until validated later. That's the intended trade-off: Method 2's job is volume + novelty, not pre-validation.

The five moves, end to end

  • Build a swipe library — a menu of proven cross-niche formats (the shape, not the subject).
  • Adapt each one to a subject inside our brand scope, naming what we own that lets us win.
  • Filter the ideas through the same two tests Methods 1 and 3 use (Ownability + Linkability).
  • Score the survivors on Beatability and Effort.
  • Deliver one CSV row per idea, in the shared merge schema.
The one rule — format honesty An imported format is only allowed if we stay honest about it, exactly as Method 1 requires:
  • The Asset title carries no shape-words (Calculator, Quiz, Generator, Interactive, Index…) — subject + angle only.
  • The Distinct angle is a content-gap deliverable from what we genuinely own or from public sources — never "add a tool", never invented data.
  • Anything that needs a real build (an interactive tool, our own original data, new primary research) is flagged in Tool escalation, never hidden — so the write phase can pick the desk-doable ideas and route the genuine builds to a human.

02The words you need first

Six terms this engine leans on. Defined once here, used the same way throughout.

Swipe library — a menu of formats that already earn links: the shape of an asset (a calculator, an index, a glossary), not its subject. Built once at Step A.
Brand scope — the shared ownership anchor brand-scope.md, built in Method 1. Every idea is judged CORE / TRANSPLANT / ADJACENT against this one file, so all three methods judge identically.
CORE / TRANSPLANT / ADJACENT — the brand-fit verdict. CORE = squarely ours; TRANSPLANT = an off-brand format re-pointed at an in-scope subject; ADJACENT = a maybe, on the edge of scope.
Format honesty — copy the real format truthfully: the title hides no shape-word, and a genuine build is flagged rather than dressed up as a desk article. The same rule Method 1 enforces.
Tool escalation — a per-idea flag: empty if a writer could ship it from public sources; otherwise one line naming what it really needs (an interactive calculator, our own survey data, new primary research).
Beatability — how easy it is to make the asset itself link-worthy (1–3). Method 2 has no in-niche competitor page to measure against, so this scores the build, not a rival.

03How it runs — one command, five scripts

A scripted pipeline, not an agent improvising. One resumable entry point runs steps A→E; each step is a script that writes one named file the next step reads. The LLM is confined to the judgment steps.

python run_model_niches.py --company <slug> — resumable: a step whose output file already exists is skipped, unless --redo (all) or --from C (that step onward) forces it. No paid API. No human gates — Method 2 is fully agent-doable (the LLM is the research tool). All LLM calls run free on the headless Claude or Codex CLI.

05Step A — the swipe library

A swipe library is a menu of formats that already earn links — the shape, not the subject. Built from two sources, then lightly pre-screened against the brand scope. Each cell in the file traces to a step, so A4 is pure assembly with nothing invented.

Pre-screen early, cut hard later A3 is deliberately light — it judges a bare format with no subject yet, so a hard "do we have an unfair advantage" test would be guesswork. 06Step B — adapt, honestly

One swipe row → one adaptation (most formats yield exactly one strong idea, not five). The b-adapt.md prompt returns fields in causal order — substance before the name — and enforces the two format-honesty rules.

For each row, the prompt is given the format shape, headline template, why it earns links, the real example, the in-scope subject, and the full brand context (brand-scope + brand-voice + features + stats). It returns:

  • Our topic — sharpen A3's in-scope subject to a precise, nameable subject grounded in the brand context.
  • Distinct angle — one line on what makes ours the link-magnet. Must name the specific product, data, or authority we own. Anti-generic test: if it could be written without the brand context, it's too generic — rewrite.
  • Asset — only now, a real working title, subject + angle, no shape-words. Never "[Format] on [topic]" glued together.
  • Tool escalation — empty if a writer could ship it from public sources; else one line naming the build it needs.
  • Headline — the published H1 in the brand voice, from the headline template (distinct from the build-name Asset).
  • What it'd be — 1–2 lines on the actual asset, concretely.

Brand fit is not asked here. A3 set the rough tag; Step C's Ownability test sets the authoritative one — deciding it a third time in B would be wasted motion.

The format-honesty fix (2026-07-22) — what changed Method 2 used to force tools dishonestly (a title like "Bad-Hire Cost Calculator" hid that it was a real build). Now the b-adapt.md prompt applies Method 1's rules: no shape-words in the title, the angle is a real content gap, and any genuine build is flagged, not hidden. Two example titles the prompt would produce for the same idea:
  • ❌ old: "Bad-Hire Cost Calculator" — shape-word in the name, build hidden.
  • ✅ new: "The Real Cost of a Bad Hire vs. the Cost of Catching Them First" — subject + angle, with Tool escalation = "interactive calculator".

07Step C + D — the gate and the score

Step A pre-screened bare formats. Step C is the real gate, run on the ideas now that each has a real subject — the same two tests Methods 1 and 3 use, against the same brand-scope.md. Expect to drop a material chunk. Then Step D scores the survivors.

Test A — Ownability

  • Does it sit inside the brand scope (CORE / TRANSPLANT / ADJACENT)?
  • Does the company have the data, product, or authority to speak credibly on it? The Distinct angle must name a specific one — if it can't, it fails.
  • Does building it reinforce the brand?

Out of scope? Run the transplant check before dropping. This CORE/TRANSPLANT/ADJACENT verdict is the authoritative Brand fit written to the CSV — it supersedes A3's rough tag.

Test B — Linkability

  • Is there a citable number the asset could produce?
  • Would a journalist reference it when writing about the niche?
  • Is it evergreen?
  • Does it fit a proven link-bait format? (Method 2 = automatically yes, so ≥2 of the other 3 needed.)

Needs ≥3 of 4 (LINKABILITY_MIN). Every KEEP / DROP / MAYBE logged with a one-line reason in run-log.md.

Real Testlify drop — what the gate caught 24 adaptations → 23 kept, 1 dropped at Step C: "An Interactive Teardown of Testlify's Video AI Interview" — "reads as a product explainer, no third-party-citable number; journalists cite data, not 'how our tool works'." A clean Linkability failure, exactly the kind the gate exists to catch.

Step D — score (same scales as Method 1)

Beatability (1–3)

  • 3 — simple format, short build (glossary, basic calculator)
  • 2 — moderate (interactive tool, data-light index, definitive guide)
  • 1 — heavy (proprietary data report, complex interactive)

Effort (S / M / L)

  • S — days to a week
  • M — weeks
  • L — a month or more

Where this sits in the bigger machine Method 2 outputs a separate pool. It is now included in the cross-method merge (4-merge, INCLUDE_M2=True / MG_INCLUDE_M2=1) — reinstated once the format-honesty fix landed. At the merge:
  • Method 1, 2, 3 pools are clubbed into clubbed-ideas.csv and de-duplicated.
  • The merge carries the Tool escalation column through, so the write phase can pick only the desk-doable ideas and route the real builds to a human.
  • The in-niche overlap check ("does a competitor already own this?") and the Build window (NOW/LATER) are decided there, where all three pools compete for the same capacity — never inside this method.
