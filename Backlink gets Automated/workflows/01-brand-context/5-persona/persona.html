Persona — who each article is written to

A one-time builder that reads the company's brand-voice document and proposes 3–4 distinct reader personas — the specific buyers each article is pitched at. It saves them as persona.md, the library every later article picks one persona from. Here's exactly how it works, script by script.

01The one idea

A persona is the reader an article targets — not the person who wrote it. It sets the depth, vocabulary, and angle of the piece. This engine defines the whole set once, from what the company already knows about its audience.

📖

Read what's already known

The audience is already captured in brand-voice.md (builder 1). The engine feeds that whole document to the model — it does not invent readers from thin air.

👥

Split "HR" into real roles

One LLM call returns 3–4 non-overlapping reader sub-personas — a recruiter, a hiring manager, an exec — each with the fields a writer needs to pitch at the right depth.

📝

Save the library in place

The set is assembled into a Markdown table and written straight to persona.md. No separate draft to promote — the git diff is the review surface.

🎯

One persona per article, later

At research time each topic is tagged with exactly one persona from this library. The write phase then targets that same reader.

The one rule that governs everything

A persona is the READER we write TO — never the author byline. It sets the lens, depth, and angle; it is not a claim about who wrote the piece (the real named author + credentials come from the separate author / E-E-A-T workflow).

  • Never invent or imply a fake author identity.
  • Picking your own audience (an HR leader, when the company sells to HR leaders) is correct — that's the point.
  • When writing, think about the persona but never name or address them in the article ("as an HR leader, you…"). Naming fences the piece to one reader when others may read it too.

02The words you need first

Four terms, defined once, used the same way everywhere below.

Persona — the specific reader an article is written to (a role + seniority + company size), used to set the piece's depth, vocabulary, and angle. Not the author, and never named inside the article itself.
brand-voice.md — the upstream document (builder 1 of this layer) that captures how the company writes and, in its Audience Understanding section, who it sells to. It is the raw material this engine reads.
Lifted verbatim — the exact prompt that proposes the personas lives in the recipe file, not in the Python. The orchestrator pulls that block straight out of the Markdown at runtime, so the prompt has one source of truth.
Write in place — the engine saves the finished persona.md directly to its real path (no throwaway draft copy). An earlier design wrote a _drafts/ copy a human had to promote by hand — that promotion step was forgotten on 5 of 6 builders, so the real file is now written directly and reviewed through git.

03The persona — its six fields

Every persona is one row with the same six fields, in the order a writer needs them. The model fills each; the code only arranges them into the table.

name
A short role label. Example: "TA / Recruiting Practitioner".
who
One line — their role, seniority, and company size. The reader in a sentence.
reads
The kinds of articles this persona is the right reader for. What routes a topic to them.
cares_about
The top 2–3 things they want or decide on. What the piece must pay off.
depth_and_angle
How to pitch to them — vocabulary, depth, and what proof convinces them. The calibration a writer follows.
not_this
What would feel off, too junior, or too generic for them. The line a section must not trip.

Alongside the personas, the same call returns one how_to_pick rule — one or two sentences on choosing the right persona for a given topic (covered in §06).

Who does what: the model judges, the code assembles

🤖

The LLM call

Claude or Codex, headless CLI · one call

Reads the whole brand-voice document and returns 3–4 distinct personas + the how_to_pick rule as JSON. This is the judgment step — which readers exist, and how they differ.

Free · no API key
Runs on the locally authenticated CLI. Provider is a one-line switch (LLM_PROVIDER, default claude).
⚙️

The orchestrator

run_persona.py · pure assembly

Lifts the prompt from the recipe, pastes the brand voice in, then arranges the returned fields into a Markdown table. It invents nothing — every cell comes from the model's JSON.

Deterministic
Warns if the model returns fewer than 3 or more than 4 personas, and writes the file atomically (temp file, then rename).

04The pipeline, step by step

One command — COMPANY=<slug> python3 scripts/run_persona.py — runs the whole thing. It is a single LLM call wrapped in read, assemble, and save.

1

Read the brand voice free code

Load the upstream document. If it isn't there, the run stops with a clear message — personas derive from it, so there's nothing to do without it.

  • run_persona.py reads 01-brand-context/brand-voice.md in full and pastes it into the prompt's {{BRAND_VOICE}} slot.
  • The Audience Understanding section is the part that matters, but the whole file is fed so the model sees the full voice.
2

Propose 3–4 personas — one LLM call free

The one moment of judgment. The prompt is lifted verbatim from the recipe, so the model, not the code, decides which readers exist and how they differ.

  • run_persona.py → _recipe_prompt() pulls the exact prompt block out of persona.workflow.md with a regex — one source of truth for the prompt.
  • llm.call_json() runs it on Claude or Codex and returns JSON: a personas array + a how_to_pick string. Bad JSON is nudged and re-asked; a hiccuping CLI is retried with backoff.
  • ↓ §07 — the gate & the reviewer-notes loop
3

Assemble the table + save code

Pure assembly — the returned fields are arranged into a Markdown table with the one-rule note on top. Nothing is invented here.

  • Writes the library to 01-brand-context/persona.md (in place) and the raw JSON to _work/persona/personas.json.
  • Both saves route through an atomic write (temp file, then rename), so a crash never leaves a half-written file.
  • If how_to_pick comes back as an object or list instead of a string, it's flattened to bullets before writing.
  • ↓ §05 — the real table it produces
4

Human gate — review the diff gate

The one human step. Because the file is written in place, reviewing means reading git diff on persona.md and editing directly — merge duplicates, sharpen a "not_this", drop or add a persona.

  • No separate draft to promote. The edited file is the deliverable.
  • To re-run with fixes folded into the prompt, use --notes-file ↓ §07.

05Real example — Testlify's four personas

The actual projects/testlify/01-brand-context/persona.md, trimmed to two of its six columns so it fits. Real data.

PersonaWho they areDepth & angle to pitch at
TA / Recruiting Practitioner In-house recruiter or TA specialist, IC to team lead, SMB through enterprise, screening high volumes. Peer-to-peer coach register, second person, hands-on. Convince with exact operational numbers and a runnable step list.
Hiring Manager (non-HR-native) A functional lead — engineering manager, ops supervisor, trades manager — who owns one role's hire. Hiring is not their day job. Their trade's language, role-specific examples, terms defined in passing. Convince with job-realistic proof of what the test asks.
HR / Talent-Management Leader HR manager to head of people, mid-to-large company, running talent reviews, succession, retention beyond hiring. Question-led, stat-backed, both-sides-honest. Convince with named research (Gallup, McKinsey, PwC) and frameworks they can present internally.
Executive & Compliance Buyer CHRO, CXO, or legally minded enterprise HR, signing off the purchase and answerable for the selection process. Measured, lawyer-passable language ("reduce bias," never "bias-free"). Convince with certifications, exact commercial terms, and audit-trail specifics.
Note

The four are deliberately non-overlapping — each reads a different kind of piece. Two personas that read the same articles are one persona, and would be merged at the gate.

06How to pick one per article

The library ships with a how_to_pick rule: route a topic to whoever decides or acts on it. One article gets exactly one persona. Below is that rule, applied to Testlify's set — real data.

Article topic / intentRight persona
Screening, hiring-process, tool-comparison how-tosTA / Recruiting Practitioner
"How to assess for [role/skill]", role interview questionsHiring Manager
Talent reviews, skills gap, workforce strategyHR / Talent-Management Leader
ROI, compliance, security, pricing, buying decisionsExecutive & Compliance Buyer
  • For a genuinely shared how-to topic, default to the more junior hands-on reader — the numbers still satisfy the senior one.
  • Candidates and test-takers who land on interview-question pages are out of scope — never write to them, even when they dominate the search traffic.
  • After drafting, verify the tag: if any section would trip the chosen persona's not_this line, re-pitch that section or re-tag the article.
Who runs this rule

This engine only writes the rule down. Downstream it runs as code:

  • The research-structure engine's pick_persona.py reads persona.md and picks the ONE persona for each asset, writing it to persona.json and embedding it in the blueprint.
  • The bundle step then reuses that picked persona — single source of truth, never re-picked (see §08).

07The gate and the iteration loop

Persona quality is a judgment call, so a human owns the final set — but re-running with feedback is scripted, not manual copy-paste.

The review surface is git, not a draft file

Because the run writes persona.md in place, there is no _drafts/ copy to promote. Reviewing is reading the change:

  • git diff persona.md shows exactly what the run proposed or changed.
  • Edit the file directly — merge overlapping personas, tighten a not_this, adjust the how_to_pick routing.
  • The edited file is the deliverable; there's no extra step to forget.

Fold review notes back into the prompt

When the set needs a real re-generation (not just a hand edit), pass the reviewer's findings back through the model:

  • COMPANY=<slug> python3 scripts/run_persona.py --notes-file notes.txt
  • The orchestrator appends the notes to the prompt under a "REVIEWER FINDINGS — implement each concretely" header, so the next run's personas answer the feedback directly.
Honest status

Two doc strings lag the code: the README.md and the run_persona.py header still mention a _drafts/persona-draft.md copy. The authoritative config.py writes persona.md in place, and that is what actually runs — this page follows the code.
