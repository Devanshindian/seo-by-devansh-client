Brand Context · Layer 01 · Engine 2

Style Guide — how the company already writes, turned into rules

One command reads the company's top 30 blogs, works out the few house choices that show up in the real writing (headline casing, Oxford comma, quote style, its industry vocabulary), and fills those into a ready-made editorial style guide. About 85% of the guide is standard best practice written straight in; the rest is observed from the real content. Here's exactly how it works, script by script.

01The one idea

A style guide is the rulebook every article is edited against — capitalization, punctuation, which words to use and avoid. Most of it is the same for any company. This engine writes that standard part straight in, and pulls the handful of company-specific choices from the real published blogs, so nothing is guessed.

📊

Pick the blogs

A script ranks the whole site by search traffic and keeps only the editorial articles — the top 30.

🔍

Read & observe

Three AI readers split the 30 blogs and report only what they see: casing, commas, quotes, terms, filler words.

🧮

Merge the votes

Code combines the three reports — majority wins for yes/no choices, lists get pooled and de-duplicated.

📝

Fill the template

The AI drops each observed value into a ready-made guide and writes the standard rules straight in.

The one rule that governs everything

Every field in the guide is filled from exactly one of three sources, and each source is tagged so it is obvious where the value came from. Nothing is invented; no section is left empty.

  • [BLOGS] — decided by reading the real top-30 blogs (from the Step 2 analysis).
  • [STANDARD] — a best-practice editorial default, written straight in (the same for most companies).
  • [COMPANY] — fill what the blogs show, then flag it for the marketing team to confirm.

02The words you need first

A few terms carry the whole page. Each is defined once here, then used the same way throughout.

Style guide — the editorial rulebook an article is checked against before publishing: capitalization, punctuation, number style, preferred and banned words, formatting, SEO meta. The deliverable this engine produces.
Editorial blog — a real content article (a how-to, a definition, a listicle), as opposed to a commercial page (pricing, product, competitor, integration) or a template/glossary index. Only editorial blogs are read, because they show how the company actually writes prose.
Signal — one observable style fact the readers extract, e.g. headline_case, oxford_comma, quote_style. Eleven signals in all. Each becomes one line in the guide.
Oxford comma — the comma before "and" in a list ("skills, speed, and accuracy"). A yes/no house choice — one of the signals the readers vote on.
Headline case — Title Case ("Top 15 Tools") versus Sentence case ("Top 15 tools"). Which one a site uses for its headings is a signal.
Verbatim template — the fill-in guide (with the [BLOGS]/[STANDARD]/[COMPANY] tags) lives inside the recipe file, and the code lifts it character-for-character at run time. It is written in exactly one place, so the recipe and the runnable pipeline can never drift apart.
body_status — a column in the site catalogue marking whether a page's full text was scraped cleanly. Only rows marked ok (and in the company's language) are eligible, so the readers never analyze a broken scrape.

03The skeleton — the files and who does the work

Six files, the standard tool-folder shape. Run it with one command: COMPANY=<slug> python3 scripts/run_style_guide.py (resumable; --redo rebuilds, --notes-file folds in reviewer findings).

FileWhat it does
config.py Every path and setting, from one anchor. Company is one env var (COMPANY). Tunables live here as named constants:
  • SG_TOP_BLOGS = 30 blogs kept
  • SG_BATCHES = 3 reader batches
  • SG_BODY_CAP = 9,000 chars of each blog fed to a reader
llm.py The one AI caller. Runs a prompt through the headless CLI — Claude or Codex (set by LLM_PROVIDER, default claude), no API key.
  • call_json — for Step 2 (parses JSON back, nudges once if it's malformed)
  • call_text — for Step 3 (returns the whole markdown document)
  • Retries a stuttering CLI with backoff; stops the run cleanly on a credit or auth error rather than burning the balance
run_style_guide.py The orchestrator plus the three step functions. Runs the steps in order, prints == Step N ==, and is resumable: each step reuses its saved output unless --redo forces a rebuild.
prompts/analyze-blogs.md The Step 2 batch prompt — the 11 signals to observe, plus the exact JSON shape to return.
prompts/fill-template.md The Step 3 fill prompt — the rules for resolving each tag type into the template.
style-guide.workflow.md The recipe (human-readable twin) — and the home of the fill-in template, which the code lifts verbatim.

Who does each job — code or the AI

⚙️

Runs in code

Deterministic. Free. No model.
  • Step 1 — pick the blogs. Read the catalogue, filter to editorial articles in the right language, sort by traffic, take the top 30.
  • The Step 2 merge. Combine the three readers' JSON: majority vote for yes/no signals, pool-and-dedupe for list signals.
Why code These are structural, repeatable choices — the same input always gives the same output. No judgment needed.
🧠

Runs on the AI Claude or Codex

Judgment. Reads prose, weighs it.
  • Step 2 — read each batch. Look at ~10 real blogs and report what the writing actually does across 11 signals.
  • Step 3 — fill the template. Drop each observed value into the guide, resolve every tag, write clean editorial rules.
Why the AI Reading prose and judging "how does this writing behave" is exactly what a model is for. The thinking is confined to these two steps.

04The full pipeline — three steps, three files

Each step writes one named file; the next step reads it. A crash resumes where it left off, because a step that already has its output file is skipped.

1

Pick the top 30 blogs free code

Read the site catalogue, keep only real editorial articles, rank by search traffic, take the top 30.

  • Keeps rows where the scrape is clean (body_status = ok) and in the company's language.
  • Editorial articles are identified by their classified type (from the sibling brand-facts engine's type-roles.json — e.g. post, hr-glossary, job-description). If that classification isn't there yet, it falls back to a URL-word test (what-, how-to, top-N, -vs-, types-of…).
  • Sorts by Traffic, takes the top 30, trims each blog's body to 9,000 chars.
  • script run_style_guide.py · pick_blogs() → _work/style-guide/top-blogs.json
↓ 05 — the three source tags
2

Analyze the blogs — three readers in parallel free Claude or Codex

Split the 30 blogs into 3 batches of ~10 and read them at the same time. Each reader reports only what it observes across 11 signals, then code merges the three reports into one.

  • Three real parallel AI calls (a thread pool, up to 3 at once) — these are the "sub-agents".
  • Each returns strict JSON: the yes/no signals, the list signals, and the free-text signals.
  • Code merges: majority wins for yes/no, pool + dedupe for lists, keep all three for the descriptive signals (so the Step 3 writer can weigh them).
  • script run_style_guide.py · analyze() · prompt prompts/analyze-blogs.md → _work/style-guide/analysis.json
↓ 06 — how the three reports merge
3

Fill the template free Claude or Codex

Take the ready-made guide template and resolve every tag: keep [STANDARD] lines as written, replace each [BLOGS] with the matching observed value, fill each [COMPANY] from the blogs and flag it for marketing.

  • The template is lifted verbatim from the recipe file, so the guide's structure lives in exactly one place.
  • After writing, the code scans for any leftover [BLOGS]/[STANDARD]/[COMPANY] tags and prints the count — the ship gate is zero unresolved tags.
  • script run_style_guide.py · fill() · prompt prompts/fill-template.md → style-guide.md
↓ 07 — what the guide covers
Written in place

Step 3 writes straight to the real style-guide.md — not a separate draft copy. An earlier design saved a _drafts/ copy that a human had to promote, and that promotion step was forgotten for 5 of 6 builders. So the review surface is now git diff on the real file.

05Deep dive — the three source tags

Every line in the template carries one of three tags. The tag decides where the value comes from and who owns it. This is the single rule that keeps the guide honest — no field is filled from thin air.

[BLOGS]

Observed from the real writing

Filled by the Step 2 analysis: headline casing, Oxford comma, quote style, industry terms, acronyms, preferred words, words to avoid. If the blogs disagreed with no clear majority, the writer picks the cleaner option and notes it rather than faking a rule.

[STANDARD]

Best-practice default

Written straight into the template, no analysis needed — numbers, abbreviations, formatting, content structure, SEO meta, accessibility. Roughly 85% of the guide. The same for most companies.

[COMPANY]

Fill, then flag for marketing

Product and feature naming, competitor rules — filled from what the blogs show, then appended with "— confirm with marketing". Never left blank, never invented as a brand preference.

06Deep dive — how the three readers' reports merge

The 11 signals aren't all merged the same way. Each falls into one of three classes, and code combines them accordingly — so three independent reads become one clean answer.

Merge classSignalsHow code combines the 3 reports
Yes/no vote
ENUM_SIGNALS		 headline_case oxford_comma quote_style Majority wins. Each reader casts one vote; the most common answer is kept.
Pool & dedupe
LIST_SIGNALS		 industry_terms acronyms preferred_words avoided_words Union of all three lists, with case-insensitive duplicates removed — so a term any reader saw survives.
Keep all three
TEXT_SIGNALS		 brand_naming em_dash_usage ellipses number_style Not merged — kept per batch ("batch1: … | batch2: …") so the Step 3 writer sees where the batches agreed or differed and weighs it.

Worked example — real, from the Testlify run (30 blogs, 3 batches)

SignalClassMerged value
oxford_commavoteYes (majority of the three readers).
headline_casevoteSentence case dominates for titles and H2s; glossary term-titles are the exception in Title Case.
quote_stylevoteCurly quotes; straight quotes essentially absent.
acronymspool~65 pooled across the batches — ATS, HRIS, DEI, FLSA, EEOC, SJT, WFM, FTE, HDHP…
avoided_wordspoolstreamline, seamless, leverage, robust, empower, crucial, holistic, "attract and retain top talent" (a pasted boilerplate line)…
em_dash_usageper-batchAll three noted true em dashes are rare and hyphens do the work — and each flagged a stray spaced colon where a dash belongs (a conversion artifact), which the writer then called out.
The point of keeping text signals per-batch

The em-dash example is why: all three readers independently spotted the same conversion artifact (a spaced colon standing in for a dash). Handing the writer all three observations, rather than one flattened summary, let it promote that shared finding into a real house rule.

07What the finished guide covers

The template is one fixed structure. Every section is always present; the tag on each line decides whether it was observed, standard, or flagged for marketing.

Grammar & mechanics

Capitalization (headlines, product names, industry terms), numbers, punctuation (Oxford comma, dashes, quotes, ellipses), abbreviations & acronyms.

Word choice

Preferred terms as "Say this → Not that" pairs, words to avoid (filler and AI-cliché hype), inclusive language.

Formatting

Bold/italic use, bulleted vs numbered lists, descriptive link text, code elements, callout boxes.

Content structure

Intro hook, one-idea sections with length targets, conclusion and CTA.

SEO-specific style

Meta title length, meta description, URL slugs, alt text.

Dates, stats, images

Date format, citing sources, presenting numbers, captions, screenshots, charts.

Brand-specific

Product and feature naming, competitor references — the [COMPANY] fields flagged for marketing.

Voice, accessibility, checklist

A short voice reminder (the full voice lives in brand-voice.md), accessibility rules, and a pre-publish editing checklist.
