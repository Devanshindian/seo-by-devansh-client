Features — the product facts every writer needs

One command turns a company's real product pages into features.md: its value propositions, full feature set, integrations, competitive differentiators, use cases, pricing, and objection answers — so any later writer can mention the product accurately and never invent a claim. Here is exactly how it works, script by script.

The idea The words The skeleton The pipeline The fact record Consolidate + seed Worked example Output + fit

01The one idea

Read every commercial page the company has, pull the real facts into eight fixed categories, then consolidate those facts into a single reference document — one entry point, run and walk away.

🔎

1. Discover

Pure code picks out the commercial pages (pricing, product, integrations, competitor comparisons) from the site catalogue — no AI, no fetching.

📋

2. Extract

One AI call per page pulls out the real facts under eight fixed categories, verbatim numbers and names.

🧵

3. Consolidate

An AI call collapses the same fact restated across hundreds of pages into one canonical line, filling the fixed schema.

🚦

4. Gate + loop

An AI judge checks completeness, facts-discipline and consolidation, then loops back to the fill step until it passes.

The one rule

Every fact in features.md comes from a real page or the human-verified seed. Nothing is invented.

  • If a fact is on no page, it becomes a > ⚑ HUMAN DECISION flag, never a made-up claim.
  • The only written (not extracted) text is the Conversion Angle — a one-line pitch per feature — and even that must be grounded in a real fact and match the brand voice.
  • This is a facts document: its whole value is accuracy. A wrong integration name or price is worse than a blank.

02The words you need first

A few terms the rest of the page leans on. Defined once, here.

Content database — content-database.csv, produced upstream by Layer 00 (the site catalogue). Every page the site has, one row each, with the page's URL, its stored body text (Full content), its classified Type, its language, and its search traffic.
Type / type-roles — the catalogue tags each page with a Type (pricing, blog, integration…). type-roles.json (from Builder 0, brand-facts) marks which of those Types count as commercial or stat pages. This is how discovery knows a product page from a blog post — no guessing from the URL alone.
Commercial page — a page that describes the product itself: what it is, does, costs, who it is for, or what it integrates with. The opposite of editorial content (blogs, guides, glossaries), which this engine skips.
Facts pool — facts.json, the raw facts pulled from every commercial page, one block per page, each sorted into the same eight categories so they can be gathered across all pages later.
Consolidation — the real work of Step 3: the same fact (e.g. "3,500+ tests") is restated on dozens of pages; consolidation collapses every instance into one canonical line, keeping the most specific / complete version.
Seed — _seed/features-seed.md, human-verified facts a crawler can never reach (prices rendered by JavaScript, absent from both the catalogue and the raw HTML). The seed is authoritative: where the crawled pool disagrees, the seed wins.
Quality gate — an AI judge that scores the draft on completeness, facts-discipline, consolidation and legally-careful fairness language, then hands back redo notes that loop into the fill step.

03The skeleton — four files, one command

The engine is the runnable twin of features.workflow.md (the recipe). The recipe is read by a human; these scripts are what actually run.

FileWhat it is
scripts/config.py The one settings hub.
  • Every path derives from a single repo-root anchor; company is one variable (COMPANY=<slug>).
  • Reads the company record company.json for brand, niche, language, domain.
  • Holds every tunable: FT_KIND_CAP=25 (per-kind page cap), FT_WORKERS=4 (parallel AI calls), FT_BODY_CAP=12000 (chars of page body per call), timeout 420s.
scripts/llm.py The one AI caller. No API key.
  • Runs each prompt through a headless CLI — Claude or Codex (set by LLM_PROVIDER, default claude).
  • call_json() for the fact / gate steps (retries once on unparseable JSON); call_text() for the fill step (returns the whole markdown doc).
  • Backs off and retries on a transient CLI hiccup; stops the run on a credit/auth failure so it never burns a dead account.
scripts/run_features.py The one entry command — runs the four steps in order, nothing else.
  • COMPANY=<slug> python3 scripts/run_features.py
  • Resumable: reuses source-pages.json and facts.json if they exist; --redo forces a re-discover.
prompts/ One prompt file per AI call — never inlined in code:
  • extract-facts.md (Step 2)
  • fill-schema.md (Step 3)
  • quality-gate.md (Step 4)

Where the thinking is code vs AI

⚙️

Step 1 — pure code

Discovery: a Python filter over the catalogue

Picking which pages are commercial is deterministic, so it is code, not an AI call. It reads the catalogue, keeps the rows whose Type is commercial (or whose URL signals pricing / integrations / a competitor comparison), and caps big kinds by traffic.

Free · no LLM
🧠

Steps 2–4 — the AI calls

Extract · Fill · Gate — the judgment steps

Reading a page for its real facts, consolidating a repetitive pool into a tight doc, and judging that doc are judgment, so they stay AI. Each is one call to the local Claude or Codex CLI.

Free · Claude or Codex · no key

Four steps, each writing a named file the next step reads. A crash resumes from the last file written.

05The fact record — eight fixed categories

Every page is reduced to the same JSON shape. Fixed categories are what let the same fact be gathered across all pages in Step 3.

featuresEach product capability + what it does (+ the user benefit, if stated).
integrationsEvery named tool / platform it connects with (+ category, e.g. ATS).
pricingPlan names, what each tier includes, the model, any trial / guarantee / discount.
competitiveAdvantages vs a named competitor — only when the page names one; kept fair.
social_proofReal numbers: customers / teams, outcome stats, ratings, certifications, awards.
audienceWho the page says the product is for + the pains it names.
ctasThe exact call-to-action button / link text on the page.
faqAny question → answer pairs on the page, verbatim.

Each category maps to a section of features.md

Step 3 gathers one category across all page blocks in the pool, consolidates it, and fills the matching section. This is the traceability map — every section traces to a named category.

features Core Value Propositions
+ Technical Features
  • The 5–10 strongest features are elevated to Core Value Props — each gets a Benefit + a written Conversion Angle.
  • The full set goes into Technical Features, grouped into 3–5 named categories.
  • "Strongest" is measured, not taste: most-recurring across the pool + cited as advantages on competitor pages.
integrations Integrations & Ecosystem Every named tool + what the integration does, grouped by type (ATS, HRIS, communication, automation…).

  • Pain → solution pairs, worded on-voice.

06The real intelligence — consolidate, then seed, then gate

Steps 2–4 look simple. The value is in three moves: collapsing a repetitive pool, letting human-verified facts override the crawl, and judging the result honestly.

Consolidate — dozens of pages into one canonical line

The pool is hundreds of near-duplicate pages restating the same facts ("3,500+ tests" can appear 30–40 times). For each category, in order: merge every instance into a single most-specific line; keep the fact, drop the marketing prose; surface the strongest features twice (once as a Core Value Prop with a pitch, once in the full Technical Features list — nothing dropped, only re-surfaced).

The hard stop

Consolidation is not cherry-picking. Every fact gathered in the pool — every feature, integration, competitive point, social-proof stat, segment, CTA and FAQ from every page — must land somewhere in features.md, or be explicitly flagged. A silently dropped fact fails the gate.

The seed — human-verified facts the crawler can't reach

Some facts are rendered by JavaScript and are absent from both the catalogue and the raw HTML — only a person with a browser can see them (for Testlify, the entire pricing table). Those live in _seed/features-seed.md, fed to the fill step as authoritative.

Seed wins

Where the crawled pool disagrees with the seed, the seed is used and the crawled variant is not even mentioned as a conflict. Stale translated pages and old competitor-comparison pages often carry outdated prices; the seed is the current truth. Keeping the seed current is the human's job (a gate in the Layer 01 run order).

The gate — four checks, then loop

CheckFails when…
Completenessa section is missing or a [BRACKET] placeholder survives.
Facts-onlya specific (a price, an integration) looks invented rather than plausibly from the pool. A ⚑ HUMAN DECISION flag is legitimate.
Consolidationa section reads like repeated marketing prose instead of one canonical line per fact.
Legalan absolute fairness claim appears — "bias-free" / "eliminates bias" is an automatic section fail.

A fail returns consolidated redo notes that feed straight back into Step 3. The loop is capped at 3 rounds so an un-satisfiable judge can't spin forever — after that it ships the best draft for human review.

Where this sits in the bigger machine

Builder 3 of 7 in Layer 01 (Brand Context), the one-time builders that learn what a company sells and how it talks.

  • Upstream: Layer 00 (site catalogue) gives the content database; Builder 0 (brand-facts) gives type-roles.json; Builder 1 gives brand-voice.md for the pitch wording.
  • Downstream: features.md is read by the asset engine (Layer 02) and the content machine (Layer 03) so any writer can mention the product accurately. It also feeds brand-scope.md, the ownership anchor the asset-idea methods share.
  • Human gate: review the diff, and fill _seed/features-seed.md with any JS-rendered facts (e.g. the price table) the crawler missed.
